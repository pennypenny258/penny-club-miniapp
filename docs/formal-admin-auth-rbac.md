# 正式运营后台会话与 RBAC 准备

## 当前状态

本阶段只完成离线契约。正式登录、管理员身份绑定、CloudBase 数据库和浏览器路由均未启用；匿名 staging 仍只能使用演示数据。不要现在执行 008、创建凭据或填写云托管变量。

正式模式只接受服务端验证后的外部身份，再签发随机、短期、可撤销的 Bearer 会话。令牌不包含角色；每次请求都从服务端重新读取有效角色和权限，因此撤销角色或会话可立即阻断后续请求。正式模式明确拒绝 Cookie、`x-demo-user`、`x-admin-role` 和前端提交的任何角色声明。

## 最小权限矩阵

| 角色 | 主要职责 | 明确不做 |
|---|---|---|
| 系统管理员 | 角色管理、会话撤销、安全就绪；应急时拥有业务权限 | 仍不能绕过 006/007 的经办人不可重复规则 |
| 运营人员 | 建导入批次、回滚、执行已独立申请的物化；资料/活动/需求日常管理 | 不复核自己导入的行，不申请物化，不批准名册 |
| 审核人员 | 行复核、申请/补偿物化、会籍重算、独立名册批准 | 不执行自己申请的物化，不管理角色 |
| 审计人员 | 只读安全就绪和脱敏审计 | 无业务写权限，不能读取 CRM/付款正文或附件 |

006/007 继续负责更细的职责分离：导入人、行复核人、物化申请人、执行人以及名册发布批准人必须按流程相互独立。RBAC 只授予“可以承担哪类职责”，不会取消这些人员不可重复条件。

## 会话与高风险操作

1. 外部身份提供方在服务端验证断言；原始 subject 不入库，只保存带服务端密钥的哈希绑定。
2. Node 生成 32 字节随机令牌，只把令牌的带密钥哈希持久化；令牌只返回一次。
3. 每次请求使用 `Authorization: Bearer …`。数据库异常、身份未绑定、会话过期/撤销、角色失效一律拒绝，不回退演示身份或内存。
4. 角色管理、会话撤销、回滚、物化、会籍重算和名册发布等高风险操作要求近期重新认证、合法幂等键，并在数据库中预留一次性操作授权。
5. 操作授权不能替代 006/007 的事务与审计；未来路由必须先完成正式会话授权，再调用对应受控服务/RPC。未完成这种顺序接线前，真实后台保持启动阻断。

## 未来 CloudBase 人工步骤（现在不要执行）

只有 004–007 已按各自清单执行并全部验证、正式后台身份提供方确定、回滚/备份窗口就绪后，才可在空测试环境依次人工执行：

1. `server/db/migrations/008_admin_session_rbac.sql`
2. `server/db/cloudbase-pg-console/540_record_admin_auth_version.sql`
3. `server/db/cloudbase-pg-console/590_verify_admin_auth_readonly.sql`，所有结果必须为 `true`

008 不会自动创建管理员绑定或角色分配。首次身份绑定必须另做有审计的引导流程，不能用浏览器表单直接写表，也不能把 API Key、身份断言、密钥或管理员 subject 发到聊天中。

未来只在 CloudBase 云托管服务端保存这些变量类别：正式认证开关与模式、外部已验证身份提供方、PG 会话存储、会话哈希密钥、subject 哈希密钥、issuer、有效期、近期认证窗口，以及既有后端网关凭据类别。不要写进小程序、浏览器代码或仓库。

生产启用还必须同时满足真实后台身份验证、008 迁移、持久审计/幂等和受保护路由接线。任一项缺失，发布检查继续失败。

## 当前唯一外部动作

本地提交完成后，只需在 GitHub Desktop 检查提交文件不包含个人配置，再点击 **Push origin**。此刻不要进入 CloudBase 执行 SQL，也不要创建或填写任何凭据。

首次管理员建立及后续角色变更继续受 `admin-bootstrap-role-governance.md` 约束；008 本身不允许自注册或自行授予角色。
