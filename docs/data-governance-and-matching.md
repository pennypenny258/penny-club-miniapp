# 数据治理与会员匹配规则

## 四个相互独立的事实域

1. **内部 CRM 核验库**：运营自行维护，用于身份、会籍到期日和群内状态核验。只允许后台受权角色访问，绝不进入会员端接口。
2. **自愿公开名册**：独立数据源。只有会员明确同意公开、运营人工审核通过，才可进入公开名册；CRM 或订单不能一键生成公开档案。
3. **付款证据**：微信小店订单、微信经营账户/商户号支付小票、个人手动转账。三者都只是匹配与续费线索，不能单独证明当前会籍有效。
4. **最终会籍判定**：运营以当前是否仍在大群作为硬门禁，并结合群标签日期、续费通知状态、CRM 与付款线索形成判断和跟进项。

后台必须同时展示 `内部 CRM 会籍核验状态` 与 `公开名册状态`，两者没有自动同步按钮。撤回公开同意只影响公开名册；会籍失效会阻止会员端访问，但不修改历史付款事实。

## 保守的当前判定基线

当前原型把大群状态作为最终硬门禁：账号未禁用且 `group_status=in_group` 才可保持当前访问；已退群、已移除或未知均进入待确认/不放行。群标签日期已到期，但成员仍在群且运营尚未通知续费时，不自动标为失效，而是进入“待续费跟进 / 仍暂时有效”。

CRM 缺项、付款线索缺项、OCR 标签或日期待确认都进入运营补全清单。它们不能凭单一来源激活会籍，也不能自动生成公开名册。运营一旦记录“已通知且逾期”，或确认成员不在大群，才结束暂缓状态并生成新的判断记录。

## 微信小店付款证据预检

预检顺序：标准化订单状态 → 检查支付/下单时间存在 → 检查手机号可用于受控匹配 → 检查商品和金额字段 → 计算退款后是否仍有正向净收款 → 应用会籍产品规则 → 人工复核。

- `cancelled / refunded / pending`：直接排除为当前有效付款证据。
- `paid / completed`：只有退款后净收款为正且命中会籍产品规则，才进入人工复核。
- `partial_refund`：无论剩余金额如何都要求人工复核。
- 人工补录/二次付款与小店证据进入同一证据表，但保留来源，不能覆盖原记录。
- 原始手机、金额、时间和商品属于受控字段；预检响应、日志和普通后台列表只返回存在性、规则匹配和判定状态，不回显原值。

## 自愿公开名册

- 原工作簿中的“姓名”不自动映射为公开名称；公开名册使用会员确认的 `public_display_name`。
- 原联系方式进入私密匹配/对接流程，不进入公开名册 CSV、列表接口或页面。
- `public_display_consent=yes`、`migration_status=ready`、`contact_mode=request_only` 才能提交人工审核。
- 人工审核通过后，仅公开同意范围内的职业资料；联系方式仍默认通过申请对接。
- 同意撤回、资料过期或会籍失效时，公开展示应及时停止并保留审计。
- 会员自助更新必须保存为新版本并经人工审核；在职名片只进入 CRM 的内部核验子状态，不能修改公开资料或触发会籍重算。

## 匹配与去重

原始联系方式应在受控导入层加密并生成不可逆、带密钥的匹配令牌；业务表只使用内部会员引用。多个相似历史工作表应记录来源工作表、批次和行指纹，先去重再合并，不能简单导入全部或默认最后一个工作表正确。

匹配冲突、一个联系方式对应多人、同一人多联系方式、不同支付渠道记录冲突时一律进入人工队列，不自动合并。

## 禁止项

- 日志、测试样例、普通后台列表、会员端和迁移报告不得输出真实姓名、手机号、订单号、地址、支付明细或联系方式。
- 禁止通过订单、CRM 或历史名册一键生成公开名册。
- 禁止以单笔小店订单直接延长或激活会籍。
- 禁止将地址、订单号、支付凭据、退款报文或原始联系方式写入公开资料字段。
