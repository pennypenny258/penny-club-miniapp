# 技术架构（MVP）

## 设计结论

采用原生微信小程序作为会员端，Node.js API 作为统一业务边界，浏览器后台供运营使用。MVP 的数据仓储为内存演示实现；生产环境将同一仓储接口替换为 PostgreSQL/MySQL，不改变页面和核心业务规则。

```text
微信小程序 ─┐
            ├─ HTTPS API ─ 认证/会籍门禁 ─ 领域服务 ─ 数据仓储
运营后台 ───┘                         ├─ 审计日志
                                      └─ 外部适配器
                                         微信登录/支付、对象存储、AI、通知、腾讯会议
```

## 安全边界

1. 客户端只展示匿名需求和公开名册字段，联系方式、公司名、交易细节、高敏感材料不进入列表接口。
2. 每次资源下载、会议链接查看、材料披露都由服务端实时复核会籍和业务授权，不依赖前端隐藏。
3. 会议特邀链接仅在运营设置的开放时间窗内向已报名且会籍有效者返回。
4. 需求披露采用申请状态机：AI 初筛 → 人工终审 → 匿名发布 → 会员申请 → Agent/运营筛选 → 需求方确认 → 定向披露/介绍。
5. 价格以订单快照保存；支付回调必须验签、幂等，成功后再延长会籍。
6. 管理员操作、导入、审核、披露、链接查看均进入不可变审计日志；生产环境需设置留存周期和访问审批。
7. 公司主体是唯一运营租户；小程序、支付商户、协议和开票主体必须保持一致或经过法务确认，配置中不得写死凭据。
8. 飞书仅作为一次性历史内容来源；迁入后正文与附件进入自有存储，访问权限由本系统重新计算。临时外部定位符不得进入会员接口，验收后清除并彻底断开来源，不做持续同步。
9. 活动通知采用持久化任务，覆盖报名成功、信息变更、会前提醒、会后归档；失败可重试且不影响报名状态。
10. 内部 CRM、自愿公开名册、付款证据与最终会籍判定是四个独立事实域。CRM/订单不能自动生成公开名册，单笔订单不能自动激活会籍。
11. 飞书 App ID、App Secret 与 tenant access token 只存在于服务端密钥/进程边界；连接状态接口只返回安全枚举，不返回请求头、原始响应、token、secret 或用户根链接。官方只读适配器可注入模拟网络和私有存储，测试不伪造真实连接成功。
12. 运营后台采用服务端 RBAC：系统管理员、运营人员、审核人员、审计人员四角色；未知角色拒绝，高风险动作需要再次确认和幂等键。演示角色请求头必须在生产删除并替换为公司身份源、MFA 与服务端会话。
13. 后台列表响应同样采用字段白名单：CRM/付款不返回原始凭据，名片不返回内容或路径，资料不返回飞书来源/附件键，需求不返回公司名、交易细节或高敏材料。
14. 标签生成分为规则建议与真实 AI/OCR 适配器两层。默认规则层不读文件正文、不调外部服务；AI 供应商、模型和凭据只能在服务端适配器边界配置，前端永不接收或回显 API key。

## 生产演进

- API：当前零依赖 Node 原型；进入联调后建议 TypeScript + Fastify/NestJS。
- 数据库：PostgreSQL（事务、JSON 字段、审计查询）；迁移工具可选 Prisma/Drizzle。
- 文件：私有对象存储，短时签名 URL，敏感文件禁止永久公网地址。
- 密钥：本机私密环境或部署平台 Secret 管理；禁止提交 `.env`、把 Secret 填入普通网页、聊天或业务数据库。
- 后台：MVP 可保留轻后台；复杂审核与表单增长后迁至 React/Vue 管理端。
- 部署：境内合规云、HTTPS、独立测试/生产环境、密钥托管、日志脱敏、备份恢复演练。
- 运维：数据库迁移版本与回滚、PITR/对象备份、RPO/RTO、结构化日志、队列积压与外部回调监控、季度恢复演练。
